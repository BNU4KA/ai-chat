# Полное задание для агента-разработчика

## 1. Цель и подтверждённые требования

Разработать приложение с простым интерфейсом чата, вдохновлённым удобством DeepSeek,
с самостоятельными ИИ-агентами через OpenRouter. Не копировать чужой бренд и ресурсы.

Подтверждено пользователем:
- React Native; iOS, Android и полноценная адаптивная веб-версия.
- Регистрация и вход через Google SSO.
- Пользователь добавляет собственный OpenRouter API-ключ.
- Ключ допустимо хранить зашифрованным на сервере.
- Аккаунты, серверная история и синхронизация между устройствами с первого релиза.
- Агенты используют инструменты: интернет, загруженные файлы, почта и календарь.
- Нужны реальные действия, а не только персонажи с разными системными промптами.

Рабочие решения, которые можно уточнять без изменения требований:
- Gmail и Google Calendar — первые почтовый и календарный провайдеры.
- Один агент с инструментами; пресеты могут ограничивать доступные инструменты.
- Поиск подключается через заменяемый серверный адаптер. Выбрать провайдера по
  доступности, цене, лицензии и качеству; записать решение перед интеграцией.
- RU/EN структура локализации; русский интерфейс первым.
- Без монетизации приложения, командных пространств, голоса, генерации изображений,
  запуска произвольного кода и координации нескольких агентов в MVP.

## 2. Правила выполнения задания

Довести разработку до проверяемого приложения, двигаясь по этапам из IMPLEMENTATION_PLAN.md.
Не ограничиваться заглушками или макетами. Не заявлять интеграцию рабочей без проверки.
Использовать актуальные совместимые стабильные версии, закрепить lockfile.
Не создавать платные ресурсы, не публиковать приложение и не загружать его в магазины
без отдельного запроса. Отсутствие внешних credentials не должно блокировать реализацию:
создать адаптер, тесты и инструкцию подключения; явно указать непроверенные live-сценарии.
Не генерировать и не коммитить реальные секреты. Не использовать рабочие аккаунты и
рабочие интеграции. Реальные отправки писем и изменения календаря тестировать только
на явно выделенных тестовых данных и с подтверждением пользователя.

## 3. Стек и ответственность компонентов

Монорепозиторий pnpm workspaces, TypeScript strict.
Клиент: Expo + React Native + React Native Web + Expo Router + TanStack Query.
Локальное UI-состояние — React state; дополнительный store только при необходимости.
Сервер: Fastify. Фоновый worker отделён от HTTP-запроса и приложения пользователя.
Supabase: Auth, PostgreSQL, Storage. Для очереди использовать PostgreSQL-backed решение
с leases/retries, например pg-boss, после проверки совместимости и требований к соединениям.
Для queue schema выделить служебные права. Не строить очередь на таймерах в API-процессе.
Общие схемы и контракты: Zod или эквивалент.
OpenRouter — серверный адаптер с потоковыми ответами и tool calling.
SSE — доставка событий клиенту; база — источник истины для восстановления.

Целевые приложения/пакеты описаны в README. Не вводить пустые абстракции без потребности.
Для продакшена API и worker должны работать на платформе с поддержкой нужной длительности
соединений и фоновых заданий. Не размещать долгие задания в короткоживущих функциях.

## 4. Пользовательские сценарии

1. Открыть приложение → войти через Google → автоматически получить аккаунт.
2. Добавить ключ OpenRouter → проверить доступ → выбрать доступную модель.
3. Создать чат → отправить сообщение → получить потоковый ответ.
4. Попросить найти информацию → увидеть инструменты и ссылки на источники.
5. Загрузить документ → задать вопрос → получить ответ с указанием документа/страницы.
6. Подключить Google → искать и читать письма и события.
7. Попросить написать письмо или создать событие → проверить точные параметры → подтвердить.
8. Закрыть приложение во время задачи → открыть на другом устройстве → увидеть её состояние.
9. Отключить интеграцию, заменить ключ, удалить чат или аккаунт.

## 5. Google SSO и сессии

Использовать Supabase Auth с Google provider. При первом входе создавать профиль по UUID
Supabase, при следующих входах использовать ту же учётную запись на всех платформах.
Email не использовать как единственный ключ владельца данных.

Web: поддерживаемый OAuth flow с корректными callback URLs и проверкой state/PKCE средствами
выбранного SDK. Mobile: выбрать поддерживаемый native ID-token flow либо системный браузер
с PKCE и deep links; проверить на development build iOS/Android, не обещать работу только в Expo Go.
Описать Google OAuth client IDs, package/bundle IDs, Android fingerprints и callback URLs.
Клиентские OAuth secrets в приложение не помещать.

Реализовать восстановление сессии, refresh, выход, отмену входа, ошибки и удаление аккаунта.
Мобильные credentials сессии хранить через защищённое платформенное хранилище с учётом
размера и рекомендаций SDK. Для web документировать выбранное хранение и защиту от XSS;
не считать browser storage эквивалентом Keychain.

Google SSO и доступ к Gmail/Calendar — отдельные согласия и жизненные циклы токенов.
При входе не просить доступ к почте и календарю. Подключать их по действию пользователя.

Для публичного iOS-релиза проверить актуальную применимость Apple guideline 4.8.
При необходимости реализовать эквивалентный privacy-preserving вход, обычно Sign in with Apple,
как релизное дополнение. Google SSO остаётся обязательным. Не считать Google-only iOS-сборку
автоматически готовой к App Store. Не объединять аккаунты по неподтверждённому email.

## 6. Ключ OpenRouter

Передавать ключ на сервер только по TLS; никогда не возвращать полный ключ клиенту.
Сохранять authenticated encryption с nonce и версией ключа шифрования; master key/KMS хранить
отдельно от БД и резервных копий данных. Предусмотреть ротацию и управление доступом worker.
UI хранит только маску, статус и дату изменения. Маска и длина не являются проверкой ключа:
проверить его через документированный API без ненужной платной генерации.

Замена/удаление ключа запрещает новые вызовы старым ключом; заранее описать поведение
текущего сетевого вызова. Ключ не попадает в prompts, tool results, exceptions, tracing и аналитику.
Нельзя хранить пользовательский OpenRouter-ключ в публичных env или клиентской сборке.

## 7. Чат и модели

Список чатов, создание, переименование, поиск по названиям, удаление с остановкой задач.
Потоковый текст, Markdown, код с копированием, ссылки, прикрепления.
Отправка, stop, повтор ответа; повтор создаёт отдельную генерацию с возможными расходами.
Изменение модели влияет на следующий запуск и сохраняется в истории запуска.
На MVP допустить только один активный запуск на чат, включая разные устройства.

Каталог моделей получать из OpenRouter, кешировать; показывать цену/контекст/поддержку tools,
если данные доступны. Не закреплять устаревающий список моделей и тарифов в коде.
Агентный режим допускает только проверенные tools-capable модели; учитывать поддержку
параметров конкретным провайдером. Не переключать на более дорогую модель незаметно.

Обрабатывать неверный ключ, недостаток средств, 429, таймауты, 5xx, ошибку внутри SSE,
обрыв сети, удалённую модель и переполнение контекста. Нельзя автоматически повторять
платный запрос после частичного ответа без явной политики и уведомления.
Бюджет контекста рассчитывать с запасом под ответ и инструменты; если нужна компрессия,
хранить исходную историю и отмечать сводку, не обрезать переписку незаметно.

## 8. Runtime агента

Цикл: история → модель → tool calls → валидация/авторизация → исполнение → tool results → модель.
Поддержать несколько tool calls, корректные call IDs и завершение цикла.
Значения по умолчанию конфигурируемые: до 10 итераций модели, 20 вызовов инструментов,
5 минут активного выполнения; ожидание пользовательского подтверждения не входит в этот срок.
Установить лимиты входа, выхода, размера файлов и результатов; финансовые оценки помечать
как приблизительные, строгий лимит токенов/шагов проверять на сервере.

Run status: queued, running, waiting_approval, completed, cancelled, failed.
Каждое событие имеет run_id, уникальный event_id и монотонный sequence.
События: run.started, message.delta, tool.started, tool.completed, approval.required,
usage.updated, run.completed, run.failed, run.cancelled.
Сохранённые события доступны по cursor; клиент применяет их без дубликатов.
Отключение SSE не останавливает run. Stop вызывает отдельную серверную отмену.

Worker использует lease/heartbeat и восстанавливает задачи после сбоя. Перед каждым новым
внешним действием проверяет отмену, владельца, разрешения и актуальность credentials.
Не обещать exactly-once для сторонних API: реализовать idempotency где возможно,
а при неопределённом результате записи сверять состояние либо останавливать на разбор;
не выполнять слепой retry отправки письма или создания события.

## 9. Инструменты и разрешения

Все инструменты имеют name, описание, input/output schemas, scopes, timeout, read/write
категорию и политику подтверждений. Модель предлагает вызов, сервер решает, разрешён ли он.
Не передавать секреты модели и не позволять задавать произвольный endpoint/command.
Недоверенные страницы, письма и файлы не могут расширять разрешения или обходить подтверждения.

Интернет: search_web и read_web_page; возвращать заголовки, URL, выдержки и время получения.
Чтение URL защищать от SSRF: адреса локальных сетей/metadata, DNS rebinding, redirects,
неподдерживаемые схемы, размер/тип контента и таймауты. Ограничивать количество страниц.

Файлы: PDF с текстовым слоем, TXT, MD, DOCX; максимум 20 MB на файл как стартовая настройка.
Проверять фактический тип, доступ, лимит распаковки и изолировать парсинг. OCR и сложные
сканированные PDF вне MVP; явно сообщать об отсутствии извлекаемого текста.
Для коротких документов использовать извлечённый текст, для длинных — поиск по chunks
с сохранением страниц/разделов и границ. Индексировать только в пределах владельца.
Storage private; доступ через авторизованные операции или короткоживущие signed URLs.

Gmail: поиск, чтение, предложение черновика, отправка после подтверждения. Создание
черновика в Gmail также является записью; локальная подготовка текста подтверждения не требует.
Вложения из почты вне MVP. Не передавать модели весь mailbox, выбирать минимум данных.

Calendar: чтение событий, free/busy, предложение создания/изменения события; запись после
подтверждения. Явно показывать IANA timezone, локальное время, участников и напоминания.
Учитывать DST; не угадывать неоднозначную дату. Удаление событий вне MVP.

Подтверждение привязано к владельцу, run, инструменту, неизменяемым аргументам, их hash,
сроку действия и одноразовому потреблению. Любое изменение аргументов требует нового
подтверждения. Закрытие интерфейса не означает согласие. Отказ возвращается агенту как отказ.

## 10. Google-интеграции

Отдельные OAuth scopes по минимальному набору возможностей; offline access для серверной
работы, refresh tokens шифруются отдельно от обычных данных. Реализовать refresh, revoke,
ошибки истечения согласия и отключение. Supabase Auth не заменяет управление refresh
provider tokens. Не считать Google-вход автоматическим доступом к Google API.
При отключении удалять локальные токены, пытаться отозвать согласие и прекращать новые вызовы.
Задокументировать Google OAuth verification и требования к Gmail scopes: публичный запуск
может потребовать верификации, а некоторые scopes — дополнительной оценки безопасности.
Не заявлять готовность публичной интеграции на основании работы с OAuth test users.

## 11. Данные и API

Предусмотреть таблицы: profiles, conversations, messages, agent_presets, runs, run_events,
tool_calls, approvals, files, document_chunks, integrations, encrypted_credentials.
Использовать FK, индексы, server timestamps и миграции. У всех пользовательских сущностей
явный owner; версии/sequence предотвращают перезапись более нового состояния старым.
Token deltas буферизовать при записи, не создавать строку БД на каждый символ.

Пользовательские таблицы и Storage защищены RLS. Таблицы секретов и служебной очереди
не доступны клиенту вообще. Supabase service role обходит RLS: каждый серверный endpoint
и worker явно проверяет владельца и scopes; не полагаться на RLS для privileged вызовов.

Минимальный API: профиль; status/save/delete OpenRouter credential; каталог моделей;
CRUD чатов; отправка сообщения с idempotency key; список сообщений; run status/cancel;
SSE events с cursor; approval accept/reject; upload/finalize/download/delete файлов;
Google integration connect/callback/status/disconnect; удаление аккаунта.
Создание сообщения и постановка run должны быть атомарны или использовать outbox,
чтобы не терять запуск и не создавать дубли при повторе запроса.

## 12. UX

Desktop web: история слева, чат по центру, настройки и выбор модели доступны без перегрузки.
Mobile: выдвижная история, корректная работа клавиатуры, safe areas, понятная кнопка stop.
Карточки действий: что читается, результат, ошибка, предложение подтверждения.
Показывать проверяемые действия и их результаты; не требовать скрытых рассуждений модели.
Light/dark, доступные подписи и фокус, кликабельные источники, длинные ответы и код.
Показывать, что запросы используют баланс пользователя OpenRouter, а не подписку приложения.
Оценки затрат отделять от фактического usage; не подменять одно другим.

## 13. Тесты и приёмка

Обязательные проверки:
- Чужие chat/file/run/approval IDs недоступны через API, Storage и privileged worker paths.
- Runtime: tool calls, malformed arguments, timeout, лимиты, отмена, approval accept/reject.
- Повтор message request создаёт один run. Две вкладки не запускают два run в одном чате.
- После обрыва SSE нет потери финала или дубликатов, после worker crash задача восстанавливается.
- Запись с неопределённым результатом не повторяется автоматически.
- Credentials не оказываются в клиенте, БД plaintext, логах и tool results.
- OAuth отмена/refresh/revoke и отключение интеграций.
- Вредоносные инструкции в письме/странице не обходят права, SSRF и подтверждения.
- Пустой, повреждённый, слишком большой файл и скан без текста обработаны понятно.
- Timezone/DST сценарии календаря.
- Сквозной сценарий Google login → ключ → чат → инструмент → синхронизация на другом устройстве.

Автоматизация: unit/integration для runtime, разрешений и контракта; web E2E критичного пути.
Native smoke на iOS и Android development builds; перечислить реально проверенные устройства.
Тестовые adapters допустимы для CI, но не выдавать их за live-проверку провайдеров.
Typecheck, lint и релевантные тесты должны проходить. Не писать тесты, которые лишь повторяют код.

## 14. Поставка и эксплуатация

Передать работающий исходный код, lockfile, .env.example только с placeholders, миграции,
инструкцию локального запуска API/worker/client и подключения Supabase/Google/OpenRouter/search.
Подготовить health/readiness endpoints, структурированные логи без секретов, retention policy,
перезапуск worker и резервное копирование с документированным восстановлением.
Удаление аккаунта отменяет задачи, отключает интеграции и удаляет данные; сроки очистки
резервных копий и минимальных технических журналов должны быть явно описаны.

README должен разделять локально проверенное, live-проверенное и требующее внешней настройки.
Составить список эксплуатационных затрат: hosting, DB, storage, search, email/monitoring при наличии.
Не создавать видимость бесплатности этих сервисов из-за пользовательского OpenRouter-ключа.

Definition of Done: все подтверждённые MVP-сценарии работают на трёх платформах;
известные внешние ограничения перечислены; ключевые проверки пройдены;
нет реальных секретов в истории Git; документация позволяет другому разработчику запустить проект.
